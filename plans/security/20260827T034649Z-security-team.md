# Establish the security team and security architecture

## Interpreted request

Add security as a first-class Cortex team. Consolidate existing
security-specific knowledge and skills under that owner. Create a concise,
evidence-backed internal security architecture that explains Nook's current
cryptography, key lifecycle, trust boundaries, authorization, protected
storage, replication, recovery, and security validation.

## Requirements

- Add security to root routing, team ownership, selective context loading, and
  cross-team delegation rules.
- Create a security team contract and focused knowledge graph.
- Move documents and skills only when security is their primary durable
  responsibility.
- Keep mixed product behavior and implementation guidance with its functional
  team and link to security authority where needed.
- Derive every cryptographic and trust-boundary statement from current code,
  manifests, tests, or an already verified Cortex authority.
- Document implemented mechanisms and known boundaries without claiming an
  unaudited guarantee.
- Extend deterministic graph, skill-owner, routing, and preflight validation.
- Complete normal review, exact-head validation, squash merge, and Workbench
  records.

## Constraints and exclusions

- Do not invent algorithms, threat models, compliance claims, controls, or
  security guarantees.
- Do not transfer portable Rust implementation ownership merely because the
  implementation is security-sensitive.
- Do not relocate mixed product specifications solely because they mention
  authentication, secrets, or encryption.
- Do not change product behavior, cryptographic formats, storage schemas,
  infrastructure, or deployment topology.
