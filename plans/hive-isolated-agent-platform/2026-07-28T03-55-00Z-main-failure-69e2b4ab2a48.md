# Main browser verification repair plan

## Interpreted request

Restore reliable Main browser verification after the retained failed Main run by
tracing the shared client-side failure, adding a focused regression, and landing
the smallest reviewed repair through a normal pull request.

## Requirements

- Preserve the failed revision and workflow evidence in the incident record.
- Diagnose all failed browser jobs and address their shared root cause.
- Add behavior-focused browser regression coverage.
- Apply the Main-equivalent browser validation label and squash-merge only after
  exact-head repository checks and readiness auditing pass.

## Constraints and exclusions

- Do not weaken security, cache isolation, or verification checks.
- Do not push directly to Main.
- Keep Workbench content public-safe and omit raw logs, credentials, and local
  environment details.

## Initial plan

1. Inspect current GitHub, incident, and retained failure evidence.
2. Isolate the shared browser/WASM lifecycle defect and add a targeted test.
3. Format, publish a focused repair PR with the required label, and follow
   repository-owned validation through review, readiness, and squash merge.
4. Verify the resulting Main workflow and record the outcome, worklog, and PR
   statistics in Workbench.

## Completion evidence

- A merged repair PR with green exact-head browser suites and green post-merge
  Main verification.
- Updated incident, linked worklog, and immutable statistics record on Workbench.

## Safety review

This plan contains an implementation summary and public workflow references only;
it contains no raw prompt, transcript, secret, private data, raw logs, local
path, or unnecessary infrastructure detail.
