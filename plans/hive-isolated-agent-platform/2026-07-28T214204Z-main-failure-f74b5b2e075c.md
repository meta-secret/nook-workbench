# Main verification repair plan

## Interpreted request

Restore reliable browser verification after the cited Main revision by finding
the shared product behavior that prevents vault unlock and extension enrollment,
then delivering and merging the smallest tested repair.

## Requirements

- Preserve the failed revision and workflow references while diagnosing retained
  browser-test evidence.
- Add a behavior-focused regression covering the failed user flow.
- Use a normal pull request with the `ci:full-e2e` label, exact-head checks,
  review resolution, squash merge, and green post-merge Main verification.
- Publish final incident, worklog, and agent-statistics records in Workbench.

## Constraints and exclusions

- Do not weaken authentication, encryption, cache isolation, or CI gates.
- Do not bypass checks or push directly to Main.
- Keep the repair limited to the root cause; do not store raw logs or sensitive
  values in Workbench records.

## Initial plan

1. Inspect failed job output, retained artifacts, relevant implementation, and
   current GitHub state.
2. Create the deterministic branch, implement the narrow behavior fix and
   regression coverage, format, and publish a pull request.
3. Apply the required label, address all current feedback and CI findings, and
   run the exact-head readiness audit.
4. Squash-merge, verify the resulting Main run, then publish the incident
   completion worklog and statistics.

## Completion evidence

- A merged repair PR with green repository-owned checks including both browser
  suites, a green post-merge Main run, and Workbench records linking the
  diagnosis and validation.

## Safety review

This plan is a public-safe summary and contains no prompt transcript, raw logs,
credentials, private data, local paths, or unnecessary infrastructure details.
