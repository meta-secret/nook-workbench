# Repair plan for failed Main extension verification

## Interpreted request

Restore Main extension verification after a transient BuildKit Dockerfile
frontend failure was not retried by the browser-image build wrapper.

## Requirements

- Diagnose the retained extension failure and preserve its workflow reference.
- Add a narrow regression test for the failed frontend-error form.
- Keep application and cache failures fail-closed.
- Publish a labeled Hive PR, validate its exact head with full browser coverage,
  squash-merge it, verify Main, and record the delivery.

## Constraints and exclusions

- Do not bypass checks, weaken cache isolation, or push directly to Main.
- Do not retry ordinary Dockerfile instruction or application failures.
- Do not include raw workflow logs, credentials, or private data in Workbench.

## Initial plan

1. Confirm the retained failure is before the first Dockerfile instruction.
2. Tighten the frontend-flake classifier and test its retry boundary.
3. Format, publish, and fully validate the exact repair head.
4. Resolve feedback, squash-merge, verify the next Main run, and publish records.

## Completion evidence

- A linked PR with targeted retry-classifier coverage.
- Successful exact-head full validation and a green post-merge Main workflow.
- A Workbench worklog that records the root cause and delivery evidence.

## Safety review

This plan is a public-safe summary. It contains no raw prompt, transcript,
secrets, private data, raw logs, local paths, or unnecessary infrastructure
details.
