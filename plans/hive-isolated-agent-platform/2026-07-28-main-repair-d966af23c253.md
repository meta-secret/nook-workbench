# Task plan

## Interpreted request

Restore trustworthy Main browser verification after the retained Main run failed,
using a minimal normal pull request if the failure remains present on the latest
integration state.

## Requirements

- Diagnose the retained Web and Extension e2e evidence without retaining raw logs.
- Add behavior-focused browser regression coverage with any product or runner fix.
- Use a labeled, reviewed pull request, exact-head readiness audit, squash merge,
  and green Main verification.
- Record the outcome, validation, and delivery statistics in Workbench.

## Constraints and exclusions

- Preserve the failing revision and workflow reference.
- Do not weaken authentication, vault storage, cache isolation, or CI checks.
- Do not push directly to Main.
- Treat an already-green successor Main run as evidence to investigate before
  creating duplicate remediation.

## Initial plan

1. Inspect the retained failures, successor commits, workflow state, and any
   existing repair branch or pull request.
2. Isolate and implement the smallest durable root-cause repair with browser
   coverage when a defect remains.
3. Format, publish the labeled pull request, and use repository-owned checks.
4. Resolve active feedback, audit exact readiness, squash merge, and verify Main.
5. Publish the incident completion record, worklog, and PR statistics.

## Completion evidence

- A linked repair pull request with the Main-equivalent browser suites green.
- A green Main run on the squash-merged head.
- Updated incident, linked worklog, and immutable PR statistics in Workbench.

## Safety review

This plan contains no raw prompt, transcript, credentials, private data, raw
logs, local paths, or unnecessary infrastructure detail.
