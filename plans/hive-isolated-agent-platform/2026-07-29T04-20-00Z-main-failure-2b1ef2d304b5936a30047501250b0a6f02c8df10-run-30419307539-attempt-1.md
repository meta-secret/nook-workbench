# Main verification repair plan

## Interpreted request

Restore green Main verification after the identified browser-suite regression by
making the smallest compatible product and regression-test change, then deliver
it through the normal pull-request and Main-validation lifecycle.

## Requirements

- Preserve the failed Main revision and its recorded workflow evidence.
- Diagnose both failed browser jobs and consult retained application evidence.
- Add behavior-focused regression coverage and run the Main-equivalent browser
  suites on the exact pull-request head.
- Apply the Hive and full-e2e labels, address active feedback, squash-merge,
  verify the resulting Main run, and record completion and delivery metrics.

## Constraints and exclusions

- Do not bypass checks, weaken cache isolation, or push directly to the default
  branch.
- Keep the change scoped to the diagnosed failure; do not include unrelated
  feature work.
- Treat credentials, raw job logs, and local infrastructure details as
  non-recordable.

## Initial plan

1. Inspect the current branch and pull-request state plus failed workflow jobs
   and retained artifacts.
2. Locate the compatibility break, implement the smallest fix, and add focused
   regression coverage.
3. Format, publish a labeled repair pull request, and use repository-owned
   exact-head checks to validate it.
4. Resolve active feedback, audit readiness, squash-merge, and confirm the
   resulting Main workflow.
5. Publish the incident update, worklog, and delivery statistics in Workbench.

## Completion evidence

- A linked repair PR with green repository-owned exact-head verification,
  including full browser suites.
- A green Main workflow for the squash-merged revision and Workbench incident,
  worklog, and statistics records linking the outcome.

## Safety review

This plan is an original high-level summary and contains no raw prompt, chat
transcript, secrets, private data, raw logs, local paths, or unnecessary
infrastructure details.
