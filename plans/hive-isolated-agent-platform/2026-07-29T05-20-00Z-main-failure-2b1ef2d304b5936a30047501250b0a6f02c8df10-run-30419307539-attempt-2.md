# Main verification repair plan

## Interpreted request

Resume the blocked Main-repair incident in a capable worker, correct the browser
regression exposed by the failed Main run, and complete the normal PR-to-green-Main
delivery lifecycle.

## Requirements

- Retain the original failed revision and workflow evidence without publishing raw logs.
- Diagnose both failed browser jobs and cover the repaired behavior.
- Use a labeled, exact-head repair PR with Main-equivalent browser checks, review
  resolution, squash merge, and green Main verification.
- Publish the incident completion context and delivery statistics in Workbench.

## Constraints and exclusions

- Do not bypass checks, weaken cache isolation, or push directly to the default branch.
- Limit the repair to the identified failure and its regression coverage.
- Do not record credentials, raw logs, local paths, or infrastructure details.

## Initial plan

1. Inspect current GitHub, Workbench, failed-job, and artifact state.
2. Reproduce the previously diagnosed browser mismatch and implement the smallest fix.
3. Format, publish the labeled PR, and validate its exact head on GitHub Actions.
4. Resolve existing feedback, audit readiness, squash-merge, and verify Main.
5. Update the incident, worklog, and statistics records.

## Completion evidence

- A linked repair PR with green repository-owned checks including full browser suites.
- A green Main run for the squash-merged revision plus linked Workbench completion records.

## Safety review

This plan is a concise original summary and contains no raw prompt, transcript,
secrets, private data, raw logs, local paths, or unnecessary infrastructure detail.
