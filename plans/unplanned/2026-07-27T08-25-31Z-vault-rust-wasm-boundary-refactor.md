# Refactor vault state across the Rust WASM boundary

## Interpreted request

Complete and deliver a broad vault-controller cleanup that moves portable
domain types and policy into Rust, keeps Svelte focused on reactive UI and
browser lifecycle work, removes abandoned or redundant TypeScript code, and
strengthens repository checks against recurrence.

## Requirements

- Replace TypeScript-owned vault, recovery, device-protection, and Sentinel
  domain states and DTO mirrors with generated Rust/WASM enums and structs.
- Remove dead state, unused class members, JSON serialization clones, redundant
  optional-state syntax, and pass-through action methods that add no boundary
  behavior.
- Preserve browser/WASM lifecycle ownership, generated-object cleanup, stable
  extension wire values, vault isolation, authentication behavior, and storage
  serialization.
- Enable unused class-member analysis across every authored web project and add
  focused preflight invariants for the newly established boundaries.
- Keep project architecture and product documentation synchronized with the
  implementation.
- Deliver through a Nook pull request, repository-owned GitHub Actions,
  actionable review resolution, exact-head readiness, and squash merge.

## Constraints and exclusions

- Generated WASM bindings are regenerated by the normal repository workflow
  rather than edited by hand.
- This is an ownership and code-quality refactor, not a user-interface redesign
  or storage-format migration.
- Cryptographic material, vault contents, credentials, and private runtime data
  must not cross new boundaries or appear in diagnostics.
- Product validation runs on GitHub Actions; only host-applied formatting and
  the applicable lightweight UI demo contract run locally before push.

## Initial plan

1. Reconcile the accumulated refactor against current `origin/main` and audit
   every changed boundary for stale symbols, ownership errors, and lifecycle
   regressions.
2. Complete Rust/WASM exports, direct Svelte consumption, dead-code removal,
   queue encapsulation, and static-analysis enforcement.
3. Apply repository formatting and the UI demo contract, then commit and open a
   focused implementation pull request.
4. Monitor repository-owned checks and current feedback, fix every finding, and
   repeat exact-head validation until readiness succeeds.
5. Squash-merge and publish the linked Workbench worklog and delivery
   statistics.
