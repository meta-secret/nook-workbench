# ARC k0s runner delivery

## Outcome

Delivered and deployed repository-scoped GitHub Actions runners on the k0s
cluster. Every selected job receives a fresh Kata QEMU microVM containing the
runner and its private BuildKit sidecar. The implementation uses neither
Docker-in-Docker nor Sysbox.

## Progress

- Installed ARC controller and runner scale-set charts at version 0.14.2.
- Qualified Kata 4.0.0 with QEMU for ARC while preserving Dragonball for Hive
  and the default cluster runtime.
- Routed eligible `preflight` and `rust:ci` jobs through the `nook-k0s` label.
- Kept complete PR, Main, release, and runtime-dependent validation on
  GitHub-hosted workers.
- Configured zero warm runners and a four-job concurrency ceiling.
- Set each job to 8 vCPU, 16 GiB memory, and 100 GiB disposable storage, with
  BuildKit garbage collection targeting 80 GB.
- Squash-merged PR 1069 and deployed merge commit
  `a9e7e0c981e97277dac894465c07f90bbb5bb9eb`.

## Implementation problems

- Dragonball 4.0.0 reproduced a ttrpc failure for the nested OCI workload and
  left stale just-in-time runners. The same workload passed with QEMU, so ARC
  alone uses QEMU.
- Early cache probes hid useful diagnostic output and resolved the build context
  from the wrong directory. The final probe is visible, repository-rooted,
  signed, and explicitly uncached.
- The Rust job required a writable artifact contract inside the disposable
  guest. Manifest contracts now enforce that path and the cache boundaries.

## Decisions

- Keep one private privileged rootful BuildKit sidecar inside each Kata guest.
  Do not operate a shared BuildKit service.
- Expose BuildKit only on guest loopback and mount no Docker socket, host path,
  or Kubernetes service-account token.
- Use a 96 GiB sparse ext4 loop image for `/var/lib/buildkit` inside the 100 GiB
  job volume so overlayfs remains isolated and predictable.
- Keep the registry main-writer credential outside the runner namespace and
  validate SeaweedFS cache access with a signed no-cache request.
