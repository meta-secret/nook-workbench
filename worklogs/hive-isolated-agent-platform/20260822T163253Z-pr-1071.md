# Private ARC BuildKit state delivery

## Outcome

Delivered ephemeral ARC runners that reuse a trusted BuildKit seed through
copy-on-write storage. Every job still receives a fresh Kata microVM, a private
privileged BuildKit daemon, and an isolated writable filesystem. PR 1071 is
merged and the exact merge is deployed.

## Progress

- Upgraded ARC, Kata Containers, k0s, and the Hive data service.
- Kept scale-to-zero behavior and raised both general and Hive scale sets to ten
  simultaneous runners.
- Added a non-destructive Btrfs pool that serves private reflink images without
  repartitioning the node.
- Reduced per-job BuildKit capacity from 100 GiB to 32 GiB and bounded garbage
  collection.
- Promoted only successful trusted smoke state after its guest stopped writing.
- Removed expected missing-manifest imports from cache-source selection.
- Routed Hive Rust verification to the dedicated `nook-k0s-hive` scale set.

- The linked hosted Hive job spent 7m34 in Rust verification and 9m36 overall.
- The merged ARC job spent 1m36 in Rust verification. Setup, checkout, private
  BuildKit connection, and Neo4j readiness took 24 seconds before that step.
- A first Main-only Hive cache publication took 37m51 after verification. It
  compiled a missing release lineage and serialized about 15.9 GiB of verified
  state; this is distinct from verification and from Zot download latency.
- The production seed reports 15.86 GiB logical data and about 120 KiB exclusive
  allocation, proving that job startup does not copy 32 GiB.
- Live builders reached about 19 GiB and 22 GiB used. The 32 GiB capacity is
  retained because 24 GiB would not provide safe publication and GC headroom.

## Implementation problems

- Fresh microVM storage eliminated repeat registry hydration, but it did not
  eliminate the first trusted publication of a new cache lineage. Verification
  timing and Main-only publication timing must remain separate metrics.
- An interactive operator exec destabilized one Dragonball sandbox during
  diagnostics. Normal workflow execution had already succeeded. Operational
  proof now relies on GitHub step data, Kubernetes state, and host telemetry
  instead of guest exec.

## Decisions

- Keep fresh scale-to-zero runners and private per-job BuildKit instead of a
  retained runner or shared writable service.
- Keep the logical BuildKit capacity at 32 GiB. Live usage makes 24 GiB too
  tight for the heaviest trusted publishers.
- Keep Dragonball for normal Hive workloads. Avoid interactive guest exec and
  use external operational telemetry for diagnosis.

## Validation

- Full format, preflight, Cortex audit, exact-head validation, current-head
  review, readiness, and session-cleanliness checks passed.
- Production reports both listeners ready with a maximum of ten runners.
- Repository variables select `nook-k0s` for trusted general work and
  `nook-k0s-hive` for Hive work.
- The exact merged Hive run completed successfully on an ephemeral ARC runner.

## Remaining work

- Continue reducing Main-only verified-cache publication latency independently
  from the completed ARC runner and Hive verification migration.
