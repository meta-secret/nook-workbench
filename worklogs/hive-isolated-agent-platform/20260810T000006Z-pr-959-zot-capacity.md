# Scale Zot for concurrent BuildKit cache traffic

## Outcome

Raised production Zot from a 50 millicpu / 128 MiB reservation and one CPU /
1 GiB limit to a one CPU / 2 GiB reservation and four CPU / 8 GiB limit. The
merged manifest is deployed, the replacement pod is ready, and authenticated
internal and public registry checks pass.

## Progress

- Measured node capacity, current cluster utilization, registry storage size,
  and bounded cold and warm storage throughput before choosing the ceiling.
- Added an infrastructure contract that pins the intended request and limit.
- Documented the operating envelope and corrected the stale loopback topology.
- Addressed and resolved the actionable review thread.
- Squash-merged PR #959 and deployed the merged resource configuration.
- Verified the live Deployment, pod readiness, resource values, and registry
  authentication paths.

## Implementation problems

- Review found that the operational capacity change was missing from the
  durable quality workflow. The documentation and topology were corrected
  before final exact-head validation.
- Zot rebuilt metadata for 2,042 cache repositories during the restart. A Main
  Hive registry login overlapped that interval and received a transient 502.
  The failed job was rerun after Zot became ready and passed.

## Decisions

- Reserve one CPU and 2 GiB so routine registry work is not starved.
- Allow four CPUs and 8 GiB for parallel transfers.
- Do not allocate eight CPUs initially. Cold storage throughput is expected to
  bound transfers, and four CPUs preserves capacity for colocated runners.
- Raise the CPU ceiling only when production telemetry proves CPU saturation.
