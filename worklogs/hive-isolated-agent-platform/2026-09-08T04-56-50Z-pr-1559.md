# Work summary

## Outcome

Persisted BBR on the registry host and affected worker, including the existing BuildKit network namespace. Restored worker scheduling after sustained-transfer verification.

PR #1559 squash-merged at 04:56:50 UTC as `09537a7f75da55eec282cc49aad4828cb4f1b431`; remote main was independently verified. Final validation jobs took 4m38s for Native Rust, 2m22s for Dylint, and 3m42s for WASM Node.

## Progress

- Compared identical registry byte ranges through public HTTPS and the existing private tunnel.
- Used controlled CUBIC/BBR/CUBIC measurements to distinguish transport behavior from short-test variability.

## Implementation problems

- Short transfers were misleading: the tunnel initially looked much faster, but longer transfers also degraded under CUBIC.
- A standard speed test measured 226.77 Mbps download and 13.36 Mbps upload. A generally slow connection or fixed low-speed data cap was not established.
- Actual BuildKit TCP connections backed off heavily amid loss/reordering on the registry path. MTU probes passed, receive windows were adequate, and no NIC drops or proxy rate limit were found.
- Existing network namespaces and existing TCP sockets retain their previous congestion-control setting. Updated the existing BuildKit namespace for new connections without restarting it.

## Decisions

- Target only the registry host and affected worker.
- Keep DNS, routing, TLS, MTU, receive buffers, and other workers unchanged.
- Allow current TCP connections to finish with their existing algorithm.
- The exact source of path loss or reordering remains unlocated. BBR is the measured corrective configuration, not proof of deliberate provider throttling.
- The corrective configuration task remains explicit, separate from automatic ARC deployment. An operator must verify sustained transfers before restoring scheduling.
