# Restore sandboxed Hive broker delivery

## Outcome

PR 804 restored the credential-free publication and authentication broker
paths used by isolated workers, reduced redundant dispatcher work, and made the
production Redis compiler-cache credential available to trusted Hive builds as
a BuildKit secret.

## Progress

- Preserved Kata Dragonball and nested Bubblewrap isolation.
- Kept GitHub and Codex credentials exclusively in broker containers.
- Added bounded release-scoped retry for exhausted Main-repair chains.
- Removed duplicate Hive workflow dispatch and retained the manual verification
  surface.
- Applied the nook-app cargo-chef and remote sccache topology to Hive builds.

## Implementation problems

The original nested sandbox could not reach the publication socket, the
dispatcher repeated unchanged Workbench fetches, and verification builds did
not consistently receive the production Redis credential. Focused Rust,
manifest, and live sandbox regressions were added before merge.

## Decisions

Workers receive only Unix-socket capabilities and never receive GitHub tokens
or unrestricted network access. Trusted Hive verification and production
release builds use the external TLS Redis cache; pull-request BuildKit layers
remain read-only consumers.

## Validation

- Exact-head PR and Hive workflows passed.
- The Hive workflow selected the persistent TLS Redis backend and reported
  1,910 compiler cache hits with zero misses.
- `task pr:ready PR=804` passed before squash merge.
- Taskfile-owned deployment and live cluster diagnostics passed.

## Remaining work

The retained Main incident still needed a worker-runtime compatibility repair,
which was delivered in the follow-up PRs linked to this plan.
