# Airbnb mixed-identity authentication simulation

## Implementation problems

- Initial hosted Core tests exposed overly broad generic classification, a contradictory low-level negative assertion, and a missing label in the popular-site fixture renderer.
- Hosted Web tests exposed that absent machine-identity attributes were being represented by invented fixture metadata.
- The first authentication-sensitive browser run exposed a missing allowlist member for `mixed-phone-or-email`, even though Core and WASM tests passed.
- The next browser run proved product navigation worked but exposed a test bug: it asserted the input after successful navigation had already removed the login DOM.
- Four unrelated `main` advances required new exact-head validations. A preliminary merge packet was halted before executing a merge command when the base moved.

## Decisions

- Kept classification and assignment policy in Rust Core; WASM remains a thin, typed, credential-free bridge and Web only collects DOM evidence.
- Required the exact Airbnb identity: same-origin `/login`, omitted GET semantics, exact phone-or-email autocomplete and label, one actionable owned `Continue` submit, no password/new-password/OTP field, and exact empty form/control machine identity.
- Treated Google and Apple controls as out-of-form alternatives, not owned submits.
- Used one fake/intercepted Chromium scenario for the extension transport/navigation boundary; no live credential, token, cookie, provider request, OAuth value, or anti-abuse payload entered the suite.
- Added future simulation fixtures only for a genuinely different authentication-page structure.
