# Work summary

## Outcome

Merged Safari browsing-data ZIP password import into the existing Apple
Passwords import path, with Safari surfaced in Import & Export labels and
export instructions.

## Progress

- Extended Apple Passwords planning to accept Safari browsing-data ZIP archives
  containing a passwords CSV, including localized CSV entry names via header
  matching.
- Switched the vault-app panel to binary CSV/ZIP import through WASM export
  bytes.
- Updated English and Russian catalogs, product spec, demo labels, and unit/e2e
  coverage.
- Split oversized local-vault import e2e into a focused Apple/Safari suite plus
  shared password-import helpers after the source-architecture gate failed.

## Implementation problems

- Initial source-architecture check failed because `local-vault-imports.spec.ts`
  crossed 1,000 lines after the Safari ZIP e2e was added. Fixed by extracting
  Apple/Safari coverage and shared open/ZIP helpers along an import-capability
  seam.
- Local sealed `task format` repeatedly stalled on heavy web-artifact rebuilds;
  rustfmt was applied with host `cargo fmt`, and web files were kept to the
  existing Prettier style without committing host dependency churn.
- Merge readiness required one `origin/main` update after checks went green.

## Decisions

- Reuse the Apple Passwords CSV parser for Safari rather than inventing a second
  accordion for the same schema.
- Import passwords and OTPAuth only; Safari bookmarks, history, extensions, and
  payment-card JSON stay out of scope.
- Prefer `Passwords.csv` in ZIP archives, then accept any CSV whose headers match
  Apple's schema to cover localized entry names.
